# 跳遠踩板與沙坑落地偵測（原型）

建立日期：2026-10-27（最後更新：2026-10-28）
狀態：原型。已在 7 支跳遠影片上試跑，7 支都有人工 GT（10/19 的 5 跳 + 0117、0118）。程式尚未整合進正式 pipeline。

## 1. 目的

從單一固定機位的跳遠影片中，自動找出以下時刻：

| 事件 | 定義 |
|---|---|
| 踩板（board contact） | 起跳腳第一次碰到起跳板的那一幀 |
| 離板（toe-off） | 起跳腳離開起跳板前，最後一個還踩在板上的那一幀 |
| 騰空最高點（apex） | 騰空段內 y2 最小的那一幀；用來找落沙，也是檢查影片開始畫分割輪廓的地方 |
| 沙坑落地（sand landing） | 腳第一次碰到沙的那一幀 |
| 裁切點 | 選手落地後開始起身的那一幀；影片只保留到這裡 |

另外找出兩個位置：

| 位置 | 定義 |
|---|---|
| 起跳線（take-off line） | 起跳板靠沙坑那一側的邊緣，在畫面中是一條斜線；正式成績從這條線量起（見第 6 節） |
| 沙坑痕跡（nearest mark） | 落地過程中，身體任何部位碰到沙的位置裡最靠近起跳線的那一點；正式成績量到這一點（見第 7 節） |

偵測時完全不使用人工 GT。GT 只用來評估誤差。

## 2. 輸入

追蹤和 pose 不重跑，直接讀取正式 pipeline 已經產生的輸出。另外會讀原始影片，用來找起跳板和做人物分割：

| 資料 | 來源檔案 | 用途 |
|---|---|---|
| 選中跑者的 bbox（原始畫面座標） | `<stem>_all_tracks.csv`，並以 `<stem>_selected_runner.json` 的 track_id 篩選 | y2（bbox 底邊）、bbox 高度；分割時用來挑出選手 |
| HRNet WholeBody23 原始關節座標 | `pose/keypoints_2d.json` | 髖部、腳踝、腳跟、大腳趾的 x；沙面 y；痕跡部位 |
| 每一幀的時間戳記 | `pose/keypoints_2d.json` 的 `timestamp_seconds` | 計算 fps，把秒數換算成幀數 |
| 原始影片 | `RUNS` 中每一跳的 `.MOV` | 第一幀找起跳板（第 6 節）；落沙 → 裁切點逐幀人物分割（第 7 節） |

**哪些步驟用到什麼**：

| 步驟 | bbox | 關節點 | 原始影片 | 人物分割 |
|---|---|---|---|---|
| 裁切（第 5 節） | ✓（高度） | ✓（髖部） | | |
| 騰空、最高點、落沙（4.1、4.2） | ✓（y2） | | | |
| 踩板、離板（4.3） | ✓（高度） | ✓（腳） | ✓（第一幀起跳板） | |
| 起跳線（第 6 節） | | | ✓（第一幀） | |
| 沙坑痕跡（第 7 節） | ✓ | ✓（沙面 y、部位） | ✓ | ✓ |

時間事件不用人物分割。騰空與落沙只用 bbox；踩板與離板另外使用第一幀偵測到的起跳板位置。

**讀原始影片一律從第 0 幀逐幀解碼，不用 seek**（`iterate_frames`）。0117、0118 這兩支 MOV 檔頭寫的幀數（517 / 602）和實際解碼的幀數（492 / 600）不同，用 `CAP_PROP_POS_FRAMES` seek 會偏 −1 到 +3 幀，分割用的畫面就會和 bbox、pose 對不上。2026-10-28 修正前，這兩支的痕跡與檢查影片都用到錯位的畫面；10/19 的 5 支不受影響（修正前後結果相同）。

**座標約定**：使用畫面像素座標，**y 往下增加**。y2 是 bbox 底邊的 y 座標。本文件只用「y2 較大 / 較小」來描述垂直位置。

**跑動方向**：目前假設選手在畫面中由右往左跑，所以「往沙坑方向的速度」= −(x 的逐幀變化量)。

## 3. 整體流程

```
pipeline 輸出（完整影片）
  │
  │  ── 裁切 ──
  ├─ 1. 粗估速度    髖部往沙坑方向速度的第 95 百分位
  ├─ 2. 高速段      速度 ≥ 粗估速度 × 50% 的最長一段（助跑 + 騰空）；參考速度 = 這一段的中位數
  ├─ 3. 錨點        高速段結束之後，速度 < 參考速度 × 35%，連續 10 幀
  ├─ 4. 坐在沙裡    錨點之後 60 幀內，bbox 高度最小的那一幀
  ├─ 5. 開始起身    bbox 高度連續 5 幀 ≥ 最小高度 × 1.2 的第一幀
  ├─ 6. 裁切        保留「追蹤開始 → 開始起身」
  │
  │  ── 偵測（在裁切後的片段上）──
  ├─ 7. 騰空段      地面 y2 − y2 > bbox 高度 × 15%，持續 ≥ 0.3 秒的最長一段
  ├─ 8. 騰空最高點  騰空段內 y2 最小的那一幀
  ├─ 9. 沙坑落地    最高點之後，y2 不再增加的第一幀
  ├─ 10. 踩板       從騰空段開頭往回找，最後一段「腳的二維速度低且接觸板面」的開頭
  ├─ 10b. 離板      同一段「腳停住」的結尾
  │
  │  ── 位置 ──
  ├─ 11. 起跳線     原始影片第一幀 → 紅色跑道中的白色起跳板 → 靠沙坑那一側的邊緣（第 6 節）
  ├─ 12. 沙坑痕跡   落沙 → 裁切點逐幀人物分割，找碰到沙且最靠近起跳線的點（第 7 節）；
  │                 每幀的輪廓與碰沙點存進 SandMark.outlines
  │
  │  ── 檢查影片（開發用，不影響結果）──
  └─ 13. 輸出影片   追蹤開始 → 裁切點；最高點 → 落沙前另外分割，落沙之後沿用 12 的輪廓（第 12 節）
```

**順序是先裁切、再偵測。** 原因如下：

- 裁切用的參考速度取自「高速段」（助跑 + 騰空），不需要先知道踩板在哪一幀。
- 落地後選手起身、走向鏡頭的段落先被切掉，偵測時不會受影響。
- 早期版本是先偵測、再裁切（參考速度取「踩板之前」的髖部速度）。兩種順序在 7 支影片上的結果完全相同，目前只保留先裁切的版本。

## 4. 偵測

### 4.1 騰空段（`find_flight`）

對每一幀做下面兩件事：

1. **算出地面 y2**：取往前 1.5 秒內的 max(y2) 和往後 1.5 秒內的 max(y2)，兩者中較小的那一個就是這一幀的地面 y2。某一邊沒有資料時，就只用另一邊。
2. **判斷是否在空中**：地面 y2 − 這一幀的 y2 > bbox 高度 × 15%，就判定為在空中。

把連續在空中的幀串成一段一段，只保留至少 0.3 秒的段落，取其中最長的一段作為騰空段。

設計理由：

- 腳踩在地上時 y2 最大，所以一段時間內的 max(y2) 就代表地面。
- 跳遠的騰空時間大約 0.5–1.0 秒。從騰空正中間往前、往後各看 1.5 秒，一定看得到踩在地上的幀。
- 選手落地後走向鏡頭時，y2 會持續增加，這只會讓「往後」那一邊的 max(y2) 變大。取兩者中較小的那一個，就會用到「往前」那一邊，它大約等於當下的 y2，所以不會被誤判成在空中。
- 門檻用 bbox 高度的比例，會隨選手在畫面上的大小自動調整。
- 0.3 秒可以排除助跑時每一步短暫離地（約 0.1 秒）的情況。

注意：偵測到的騰空段只用來**定位**，它比實際的「離板 → 落沙」短（剛離板和快落地時，y2 差距還沒超過門檻）。精確的踩板幀和落沙幀，由 4.2、4.3 另外決定。

### 4.2 沙坑落地（`find_sand_landing`）

1. y2 先做 5 幀中值濾波（`smoothing`），去掉偵測框單幀的抖動。
2. 在騰空段內找平滑後 y2 最小的那一幀（騰空最高點）。輸出的 `JumpEvents.apex` 仍用原始 y2。
3. 從最高點到騰空段結束後 10 幀之間，找出平滑後 y2 逐幀增加量最大的那一幀（下降最快的時候）。
4. 從「下降最快」和「騰空段結束前 2 幀」（`search_before_flight_end`）兩者中較晚的那一幀開始往後找，第一個「接下來 3 幀內 y2 增加不到 3 px」的幀，就是落沙幀。
5. 檢查結果（`review_sand_landing`，輸出到 `JumpEvents.sand_landing_review` 和 `jump_event_row` 的 `sand_landing_review` 欄）：找不到落沙時標 `sand_landing_not_found`；落沙比騰空結束晚 0.25 秒以上（`max_after_flight_s`）時標 `sand_landing_late_after_flight`。有標記的跳要人工確認。

設計理由：

- 落地時身體最低的部位是腳，bbox 底邊幾乎就是腳的位置。腳被沙接住之後，y2 就不再增加。
- **平滑**：偵測框單幀跳 10 px 以上很常見（手腳張開、揚沙）。沒有平滑時，單幀尖峰會被當成「下降最快」，或讓下降途中看起來像「停住」。
- **不早於騰空結束**：騰空偵測還判定在空中的時候，腳不可能已經碰到沙。這條物理順序擋住平滑後仍殘留的較長抖動。
- 2026-11-08 以前只有步驟 3、4 的「下降最快之後」條件，16Pro 第07跳因此判早 23 幀：最高點那一幀 bbox 抖了 +12 px，被當成下降最快，接著空中有一小段 bbox 沒動，就被判成落沙（見 9.6）。

### 4.3 踩板與離板（`find_board_contact_with_board`）

1. 第一幀偵測白色起跳板，建立到起跳板 mask 的距離圖。
2. 左右腳分別計算二維速度：腳踝、腳跟、大腳趾座標的平均，再計算 `sqrt(dx² + dy²)`。
3. 速度以 bbox 高度與 FPS 正規化，並做 3 幀中位數平滑；「腳停住」= 每秒移動量 < 2.7 個 bbox 高度。
4. 從騰空段開頭往回找最後一段「同一隻腳停住」的區間，先取得起跳支撐期；這一步不要求腳一定靠近白色板，所以板前起跳不會漏掉。
5. 「腳靠近板」= 腳跟、大腳趾或小腳趾到起跳板 mask 的最短距離 ≤ bbox 高度 × 3%。候選腳中優先選實際接觸板面的腳，再比較支撐結束時間；若支撐期碰到板，就以靠近板的第一、最後一幀精修踩板與離板，完全沒碰板則保留速度支撐期。
6. 對起跳腳在支撐期間的大腳趾與小腳趾，計算相對靠沙坑側起跳線的最小水平淨距。分類為：越線 `OVER_LINE`、鞋底碰板 `ON_BOARD`、未碰板且在線後起跳 `BEFORE_BOARD`。

設計理由：

- 腳一碰到地面，二維速度會降到低檔；二維速度負責排除只有 x 不動、但 y 正在擺動的非支撐腳，起跳板幾何則負責優先選出真正接觸板面的候選腳與分類起跳位置。
- 腳趾越線是 2D 影像幾何結果，不等同正式裁判判決；仍受關節點誤差、鞋尖和腳趾關節位置差異、相機位移影響。
- **離板**（`find_toe_off`）：從踩板幀往後，走到「腳停住」那一段的最後一幀。10/19 的 5 跳誤差在 0 到 +2 幀之間（見 9.1），偏晚的原因是腳尖離地前的最後一兩幀，腳的水平速度還沒超過門檻；但 0117、0118 兩跳都是 −1（見 9.2），方向相反。
- 騰空段的開頭（4.1）比 GT 離板晚 2–5 幀，不能拿來當離板。

## 5. 裁切（`find_trim_end`）

| 步驟 | 規則 | 設計理由 |
|---|---|---|
| 粗估速度 | 髖部往沙坑方向速度（9 幀中位數平滑）的第 95 百分位 | 最快的幀一定是助跑和騰空，用來粗略分出「快」和「慢」 |
| 高速段與參考速度 | 速度 ≥ 粗估速度 × 50% 的最長一段；參考速度 = 這一段的中位數 | 錄影開頭一定有幾步助跑，最長的高速段就是助跑 + 騰空；不需要先知道踩板 |
| 錨點 | 高速段結束之後，第一個「速度 < 參考速度 × 35%、連續 10 幀」的地方 | 落進沙坑後身體被沙擋住，速度驟降 |
| 坐在沙裡 | 錨點之後 60 幀內，bbox 高度（5 幀中位數平滑）最小的那一幀 | 坐下或跪下時 bbox 高度最小 |
| 開始起身 | 從最小高度那一幀往後，第一個「bbox 高度連續 5 幀 ≥ 最小高度 × 1.2」的幀 | 起身時 bbox 高度持續增加；20% 遠大於 bbox 的雜訊，又會在起身剛開始時就觸發 |
| 裁切 | 保留從追蹤開始到「開始起身」那一幀 | 保留多少由選手的動作決定，不用固定幀數 |

**找不到時一律不裁切**：找不到高速段、找不到錨點、或找不到起身的時刻，都保留整段。多保留幾幀不影響分析，但切掉落地那一刻就找不回來了。

## 6. 起跳板位置（`detect_board`、`fit_takeoff_line`）

起跳板不會動，所以不需要逐幀偵測：每支影片只用**第一幀**算一次，得到一條起跳線。這一步**只讀原始影片**，不使用 pipeline 的輸出，也不依賴第 4、5 節的結果。

### 6.1 為什麼不用 AI 模型

- COCO 等常見資料集沒有「起跳板」類別，現成的物件偵測模型都不認得它。
- 開放詞彙模型（YOLO-World、Grounding DINO、OWLv2）可以用文字提示去找，但起跳板在 1080p 畫面中只有約 75×22 px，又是白色細條；畫面中同樣是白色的還有沙坑、跑道白線、角錐等，用文字提示很容易抓錯。
- 機位固定，起跳板的外觀單純（白板嵌在紅色跑道裡），用傳統影像處理就足夠，而且不需要下載模型權重。

### 6.2 步驟

| 步驟 | 規則 | 設計理由 |
|---|---|---|
| 1. 取畫面（`read_first_frame`） | 讀影片的第一幀 | 機位固定，起跳板在每一幀的位置都一樣；第一幀時選手還在助跑道遠端，不會擋住起跳板。單幀讀取加偵測約 0.2 秒；原本用 40 幀中位數背景約 3.2 秒（見 6.4）。0311 因攝影機中途被移動，第一幀的起跳線偏了約 6 px（見 9.3） |
| 2. 紅色跑道（`red_runway_mask`） | HSV 色相 ≤ 10 或 ≥ 165、飽和度 > 70、亮度 > 50 | 跑道是紅色的 PU；OpenCV 的色相範圍是 0–179，紅色分在兩端 |
| 3. 白色區塊（`white_mask`、`detect_board`） | 飽和度 < 60、亮度 > 160 的像素，先做 3×3 開運算去雜點，再找連通區塊；只留面積 150–5000 px 的區塊 | 整片沙坑是白色的，會連成一塊很大的區塊，因而被面積上限排除 |
| 4. 挑出起跳板（`detect_board`） | 每個白色區塊往外擴 6 px 形成一圈外環，算外環中紅色跑道像素的比例；取比例最高的區塊，比例須 ≥ 0.5，否則判定為找不到 | 起跳板是四周都被紅色跑道包住的白板。沙坑角落、場邊白線等白色物件的外環多半是綠色草皮或沙，紅色比例低 |
| 5. 起跳線（`fit_takeoff_line`） | 取起跳板區塊每一列最靠沙坑那一側的像素（沙坑在左就取最左邊的點），用 Huber 穩健擬合成一條直線，輸出這條線在區塊 y 最小、y 最大兩列的端點 | 起跳線就是起跳板靠沙坑那一側的邊緣。因為透視，起跳板在畫面中是一條斜的白條，所以要擬合成斜線，不能只取一個 x |

### 6.3 參數

| 參數 | 預設值 | 意思 |
|---|---|---|
| `ring_px` | 6 px | 外環寬度 |
| `min_area` / `max_area` | 150 / 5000 px | 白色區塊面積範圍 |
| `min_ring_red` | 0.5 | 外環紅色比例的下限。7 支影片中起跳板最低 0.59（0118 板上放了東西），其他候選最高 0.42 |
| `pit_side` | `left` | 沙坑在畫面的哪一側，決定取每列最左或最右的點 |

### 6.4 曾經失敗的做法

第一版是先找出「最大的紅色區域」當作跑道，再在跑道內找最大的白色區塊。0311、0117、0118 都抓錯了，原因有兩個：

- 沙坑邊緣也是紅色的，跑道區域會延伸到沙坑角落，把一角的沙誤判成起跳板。
- 0117 的紅磚牆也被算進紅色區域。

改成「看白色區塊的外環是不是紅色」之後，7 支影片都正確（見 9.3）。

第二版用 40 幀的逐像素中位數當背景，目的是把選手去掉。測試後發現第一幀就夠：每 10 幀單獨偵測一次，只有選手剛好踩在板上的那一幀會失敗，而第一幀不會發生這種情況。中位數背景需要約 3.2 秒，大部分時間花在跳到各幀解碼和算中位數，所以改用第一幀。

### 6.5 用途（尚未實作）

- **離板距離**：起跳腳腳尖到起跳線的距離，代表浪費掉的起跳距離；腳尖越過起跳線就是踩線犯規。
- **正式成績**：從起跳線，沿著垂直於起跳線的方向，量到沙坑中最靠近起跳線的痕跡（痕跡偵測見第 7 節）。
- 要把像素換成公尺，還需要場地標定。起跳板的標準長度是 1.22 m，可以當作沿起跳板方向的比例尺，但沿跑道方向的比例還需要其他標定點。

## 7. 最靠近起跳線的沙坑痕跡（`find_sand_mark`）

跳遠成績量的是「起跳線到沙坑中**最靠近起跳線的痕跡**」，身體任何部位留下的都算，不一定是腳。這 5 跳中有 3 跳最近的痕跡是臀部：選手落地後往後坐，臀部的位置比腳更靠近起跳板。所以只看落地瞬間的腳不夠，要看整段落地過程。

### 7.1 為什麼用人物分割，不用關節點

- HRNet 沒有臀部的關節點；手和膝蓋陷進沙裡時，關節點也常常抓不準。
- 人物分割（YOLO26x-seg）給的是整個身體的輪廓，輪廓最下緣碰到沙的位置就是痕跡，不需要知道是哪個部位。
- 關節點只用來**標示**痕跡是哪個部位（第 7.2 節步驟 6），不影響痕跡位置。

### 7.2 步驟

| 步驟 | 規則 | 設計理由 |
|---|---|---|
| 1. 搜尋範圍 | 從沙坑落地幀（4.2）到裁切點（第 5 節，選手開始起身） | 起身之後的腳印不算成績；選手離開沙坑時留下的腳印也就不會被算進去 |
| 2. 選手輪廓（`RunnerSegmenter`，細節見 7.5） | 每一幀用 YOLO26x-seg 分割所有人，取 bbox 和追蹤 bbox 的 IoU 最大的那一個 | 畫面中可能有其他人（教練、工作人員），用追蹤結果鎖定選手 |
| 3. 沙面 y（`sand_surface_y`） | 落沙幀時，兩腳腳跟、大腳趾、小腳趾 y 的最大值 | 落沙那一刻腳就踩在沙面上 |
| 4. 碰到沙（`board_side_contact`） | 輪廓每一欄取最下緣的像素，y ≥ 沙面 y − bbox 高度 × 3% 就算碰到沙 | 容許值隨選手在畫面中的大小調整；舉在空中的手、還沒坐下的臀部不算 |
| 5. 痕跡點（`find_sand_mark`） | 每一幀取碰到沙的欄中 x 最大的那一點（選手由右往左跳，x 越大越靠近起跳板），整段時間再取 x 最大的 | 對應規則「最靠近起跳線的痕跡」；同時得到痕跡出現在哪一幀 |
| 6. 部位（`nearest_scored_joint`） | 痕跡幀中離痕跡點最近、score ≥ 0.3 的 WholeBody23 關節：髖 → 臀部，腳踝/腳跟/腳趾 → 腳，手腕 → 手，膝 → 膝 | 只用來標示，不影響位置；低分數的關節常是錯的點，所以略過 |

輸出（`marks` 指令）：每支影片的痕跡幀、痕跡座標、部位、落沙時腳的接觸點、起跳線在痕跡 y 的 x 座標、起跳線到痕跡的水平像素差；有人工紀錄的影片另外列出差距。

### 7.3 容許值怎麼訂的

| 碰沙容許值（bbox 高度的比例） | 結果 |
|---|---|
| 4% | 0314、0319 會抓到還沒碰到沙的臀部弧線 |
| 1–2% | 0320 的腳跟抓不到（沙面 y 是用陷進沙裡的腳趾估的，比腳跟的 y 大） |
| **3%（採用）** | 兩種錯誤都沒有發生 |

這個值只看這 5 跳調出來，需要更多影片確認。

### 7.4 用途（尚未實作）

- 起跳線（第 6 節）到痕跡點的距離就是正式成績，但目前只有像素差。透視會讓遠近的比例不同，換成公尺要先做地面標定（homography）。
- 起跳腳離板的位置（4.3 的「腳停住」段落）到痕跡點的距離是「實際跳了多遠」，跟正式成績的差就是浪費掉的起跳距離。

### 7.5 人物分割（`RunnerSegmenter`）

| 項目 | 做法 |
|---|---|
| 模型 | YOLO26x-seg（Ultralytics 官方 COCO 權重，`models/yolo26x-seg.pt`），只取 person 類別 |
| 輸入 | **整張原始畫面**（1920×1080），推論尺寸 imgsz 1280，信心 ≥ 0.2；不先用 bbox 裁切 |
| 遮罩 | `retina_masks=True`，遮罩直接是原始解析度；機率 > 0.5 的像素算選手 |
| 挑出選手 | 偵測到的每個人，算它的 bbox 和追蹤 bbox 的 IoU，取最大的那一個；**沒有 IoU 下限** |
| 略過的幀 | 這一幀沒有追蹤 bbox，或模型沒有偵測到任何人 |
| 存下來的結果 | 每一幀的外輪廓（`cv2.findContours`，只取最外圈）和碰沙點，存成 `RunnerOutline`，放在 `SandMark.outlines[幀號]` |

**只在需要的區間分割**：

| 區間 | 分割嗎 | 原因 |
|---|---|---|
| 助跑、踩板、騰空上升（追蹤開始 → 最高點前） | 不分割 | 時間事件只用 bbox 與關節點（第 2 節的表），沒有任何偵測用到這段的輪廓 |
| 騰空下降（最高點 → 落沙前） | 只有輸出檢查影片時分割 | 只是為了在影片上看落地前的身形，不影響結果 |
| 落沙 → 裁切點 | 分割（`find_sand_mark`） | 找沙坑痕跡；輸出影片時直接沿用，不重算 |

和整段影片都分割相比：

- **結果完全相同**：痕跡只在落沙 → 裁切點這段找，其他區間的分割本來就沒被用到。7 支影片的 `mark_results.csv` 和 `mark_sheet.jpg` 逐位元組比對都相同。
- **省下的運算**：輸出檢查影片時，7 支影片的分割次數從整段都分割的 1637 次降到 638 次；每幀約 15.7 ms（見 9.5）。
- **前提**：落沙幀與裁切點要先找對。如果落沙偵測得太晚，最早的碰沙點就不在搜尋範圍內；這一點和整段分割無關，因為整段分割時也只會在這個範圍裡找痕跡。

## 10. 限制

1. **跑動方向寫死成由右往左**：換機位時，速度的正負號要反過來，或改成自動判斷方向。
2. **前提是固定機位**：鏡頭跟拍或平移時，畫面速度不等於選手速度。
3. **一支影片只能有一跳**：只取最長的那一段騰空。
4. **門檻是看同一位選手的 5 跳訂的**：需要更多選手、更多場次的 GT 才能確認泛化能力。
5. **落地後保留時間沒有上限**：選手如果在沙裡坐很久，就會保留很長（例如 0117 保留了 4.4 秒）。
6. **足部左右標籤仍依賴姿態模型**：二維速度與板面接觸可穩定事件時間，但姿態模型若左右腳標籤互換，解剖學上的起跳腳側別仍可能錯誤；例如 0118 的事件時間正確，但模型選為 right、GT 標為 left。
7. **起跳板偵測的前提**：
   - 機位從第一幀到跳躍都不能動，否則起跳線會偏（例如 0311 偏了約 6 px）；
   - 第一幀時起跳板沒有被遮住，例如有人站在板上或板前；
   - 跑道是紅色、起跳板是白色。
   
   起跳線在畫面中只跨約 20 列像素，精度大約是幾公分。
8. **起跳線只有像素座標**：還沒有換算成公尺，也還沒有和踩板、落沙的位置結合來算距離。
9. **沙坑痕跡的沙面 y 是估出來的**：用落沙幀的腳部關節點估，而且假設選手落地那條線上的沙面在畫面中是水平的。選手落在沙坑邊緣、或腳部關節點錯誤時可能會偏。
10. **沙坑痕跡被身體擋住時看不到**：例如手撐在身體後方、被身體遮住時，分割輪廓不會包含它。
11. **沙坑痕跡要逐幀跑人物分割**：搜尋範圍越長越久（0117 有 266 幀）。用 GPU 跑 `marks`，7 支影片合計約 15 秒（含載入模型、從第 0 幀逐幀解碼）；各階段耗時見 9.5。
12. **分割挑選手沒有 IoU 下限**：選手被其他人擋住、或模型漏掉選手時，會拿 IoU 最大的另一個人來用。目前沒有處理這種情況。
13. **痕跡對落沙幀很敏感**：搜尋範圍從落沙幀開始，沙面 y 也用落沙幀的腳估。落沙偵測偏早時，還在空中的腳跟會被當成碰沙（0117 因此多了 15 px）。

## 12. 檢查影片（`JumpReviewVideo`，`videos` 指令）

開發用，不影響任何偵測結果。每一跳輸出原速和 4 倍慢動作兩支，內容相同：每一幀畫好後同時寫進兩支影片，慢動作版的播放速率是 fps ÷ 4，不補幀。

**範圍**：從追蹤開始到裁切點（第 5 節）。

**分割範圍**：只在「騰空最高點 → 裁切點」做人物分割（理由與比較見 7.5）。
